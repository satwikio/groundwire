A wireless telemetry bridge, built from parts already on the bench.

One flight controller's MAVLink stream now reaches a ground PC over the Siyi MK32's Ethernet bridge — no telemetry radio, no VPN, no internet relay. This report documents what was built, how to rebuild it from nothing, the tests that prove it works, and the path from one drone to five.

Airframe under test: PX4 / ArduPilot companion link Companion computer: NVIDIA Jetson Link hardware: Siyi MK32 Date: 2026-09-17

01 What we achieved

A single drone's MAVLink telemetry is now reachable from any UDP-speaking ground station on the network — proven with live data, not just a running service.

  • ✓
    No telemetry radio neededThe Siyi MK32 already bridges Ethernet transparently between air and ground — the flight controller's MAVLink stream rides that same link instead of a separate 915/433MHz telemetry radio.
  • ✓
    No VPN or internet relay neededThe MK32 bridge is Layer-2, not routed — the Jetson's own IP is directly reachable from the ground PC. The "MAVLink-over-the-internet" pattern this project started from turned out to be unnecessary; a local UDP endpoint is sufficient.
  • ✓
    Reproducible with one scriptsetup_single_drone_telemetry.sh auto-detects the flight controller, installs/configures mavlink-router, and self-tests with live data before declaring success. No manual steps to memorize.
  • ✓
    Hardware-agnostic, proven across two flight controllersThe same script correctly picked up a PX4 FMUv6C in one session and a CubePilot Cube Orange+ in a later session, with zero code changes — see Evidence.
  • ✓

02 How it's wired

The flight controller never touches the network directly. A Jetson sits between it and everything else, turning a USB-serial MAVLink stream into UDP that the whole bridged network can reach.

Command traffic (arm, RTL, mission upload) rides the same UDP socket back the other way — the diagram shows the direction telemetry flows, but the link is bidirectional by nature of UDP + MAVLink.

03 Rebuild it from nothing

Everything below is encoded in one idempotent script. This walks through what it does and why, so it isn't a black box.

Prerequisites

Flight controller connected to the Jetson over USB and powered on. The Jetson's Ethernet port already has an IP on the same subnet the ground PC will reach it on (in this build: the Siyi-bridged 192.168.144.0/24 network). A user account with sudo.

Get the script and run it

On the Jetson:

~/drone-telemetry-setup/setup_single_drone_telemetry.sh
# make it executable, then run it
chmod +x setup_single_drone_telemetry.sh
./setup_single_drone_telemetry.sh

It will ask for your sudo password twice (once to install, once to configure) — that's normal, mavlink-router runs as a system service.

What happens under the hood

Six steps, each printed to the terminal as it runs:

  1. Find the flight controller. Looks in /dev/serial/by-id/ first (identifies the exact board by name), falls back to /dev/ttyACM0//dev/ttyUSB0. This is why the same script worked unmodified on two different flight-controller models.
  2. Confirm the Jetson's network address is already set — the script doesn't configure networking, only checks it.
  3. Fetch mavlink-anywhere if it isn't already cloned alongside the script.
  4. Install mavlink-router (skipped automatically if already built).
  5. Configure it headlessly — no interactive prompts — wiring the flight controller's serial port to a UDP server on port 14550 that any GCS can connect to, plus two loopback outputs (14540 for MAVSDK, 14569 for mavlink2rest) for future use.
  6. Self-test. Opens a UDP socket, waits 5 seconds for real bytes, and checks the first byte is 0xFE or 0xFD — the actual MAVLink v1/v2 frame markers. A running service isn't proof of a working link; bytes are.

Verify any time

# one-line status: is it running, what's it routing
mla status

# live log of the router itself
sudo journalctl -u mavlink-router -f

Connect a ground station

From the PC, point QGroundControl / Mission Planner / MAVSDK at:

UDP  →  <jetson-ip>:14550
# example from this build:
UDP  →  192.168.144.31:14550

The full script

Saved on the Jetson at ~/drone-telemetry-setup/setup_single_drone_telemetry.sh. Copy this same file onto each of the other four Jetsons for the fleet build in Section 05.

#!/usr/bin/env bash
#
# setup_single_drone_telemetry.sh
#
# Sets up mavlink-router on this Jetson so that any MAVLink Ground Control
# Station (QGroundControl, Mission Planner, MAVSDK, etc.) reachable over the
# network can pull live telemetry from the flight controller plugged into
# this Jetson via USB.
#
# WHAT THIS SCRIPT DOES (in order):
#   1. Finds the flight controller's USB serial device automatically.
#   2. Clones mavlink-anywhere (https://github.com/alireza787b/mavlink-anywhere)
#      if it isn't already present next to this script.
#   3. Installs mavlink-router (skips rebuild if already installed).
#   4. Configures mavlink-router in headless (non-interactive) mode:
#        - Input:  the flight controller's USB serial port
#        - Output: a UDP server on 0.0.0.0:14550 that any GCS on the network
#                  can connect to, plus local loopback outputs for MAVSDK
#                  (14540) and mavlink2rest (14569) if you use those later.
#   5. Starts and enables the mavlink-router systemd service (survives reboot).
#   6. Runs a live self-test: listens on the local MAVSDK UDP port and checks
#      that real MAVLink bytes (starting with 0xFE or 0xFD) are actually
#      arriving from the flight controller -- not just that the service is
#      "running".
#
# REQUIREMENTS:
#   - Flight controller (Pixhawk/PX4 or ArduPilot) connected to this Jetson
#     via USB, powered on.
#   - This Jetson's network-facing Ethernet port already has an IP address
#     on the same subnet your ground station will reach it on (e.g. the
#     Siyi MK32 / 192.168.144.0/24 network). This script does not configure
#     that -- it only asks you to confirm it.
#   - sudo privileges (you will be prompted for your password interactively).
#
# USAGE:
#   chmod +x setup_single_drone_telemetry.sh
#   ./setup_single_drone_telemetry.sh
#
# You can re-run this script safely at any time -- it is idempotent.

set -euo pipefail

SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
MAVLINK_ANYWHERE_DIR="${SCRIPT_DIR}/mavlink-anywhere"
MAVLINK_ANYWHERE_REPO="https://github.com/alireza787b/mavlink-anywhere.git"

BAUD="57600"          # Ignored for USB (CDC-ACM) flight controllers, kept for UART boards.
GCS_PORT="14550"      # Standard MAVLink GCS port. QGroundControl/Mission Planner expect this.

bold()  { printf '\033[1m%s\033[0m\n' "$*"; }
info()  { printf '  [->] %s\n' "$*"; }
ok()    { printf '  [OK] %s\n' "$*"; }
warn()  { printf '  [!!] %s\n' "$*"; }
fail()  { printf '  [XX] %s\n' "$*"; exit 1; }

bold "=================================================================="
bold " Step 1/6 - Locate the flight controller's USB serial device"
bold "=================================================================="

FC_DEVICE=""
if [[ -d /dev/serial/by-id ]]; then
    for dev in /dev/serial/by-id/*; do
        [[ -e "$dev" ]] || continue
        FC_DEVICE="$(readlink -f "$dev")"
        info "Found by-id device: $(basename "$dev") -> ${FC_DEVICE}"
        break
    done
fi
if [[ -z "$FC_DEVICE" ]]; then
    for candidate in /dev/ttyACM0 /dev/ttyACM1 /dev/ttyUSB0; do
        if [[ -e "$candidate" ]]; then
            FC_DEVICE="$candidate"
            break
        fi
    done
fi

if [[ -z "$FC_DEVICE" ]]; then
    fail "No flight controller serial device found. Plug in the FC via USB, power it on, and re-run this script."
fi
ok "Flight controller device: ${FC_DEVICE}"

bold ""
bold "=================================================================="
bold " Step 2/6 - Confirm this Jetson's network address"
bold "=================================================================="
info "Current IPv4 addresses on this Jetson:"
ip -4 -o addr show | awk '{print "        " $2, $4}'
echo ""
read -r -p "  Is this Jetson's Ethernet IP already set and correct above? [y/N]: " ip_confirm
if [[ ! "$ip_confirm" =~ ^[Yy] ]]; then
    fail "Set a static IP on this Jetson's Ethernet interface first, then re-run this script."
fi

bold ""
bold "=================================================================="
bold " Step 3/6 - Get mavlink-anywhere"
bold "=================================================================="
if [[ -d "$MAVLINK_ANYWHERE_DIR" ]]; then
    ok "mavlink-anywhere already present at ${MAVLINK_ANYWHERE_DIR}"
else
    info "Cloning mavlink-anywhere..."
    git clone --depth 1 "$MAVLINK_ANYWHERE_REPO" "$MAVLINK_ANYWHERE_DIR"
    ok "Cloned."
fi

bold ""
bold "=================================================================="
bold " Step 4/6 - Install mavlink-router"
bold "=================================================================="
( cd "$MAVLINK_ANYWHERE_DIR" && sudo ./install_mavlink_router.sh )

bold ""
bold "=================================================================="
bold " Step 5/6 - Configure mavlink-router (headless, non-interactive)"
bold "=================================================================="
(
    cd "$MAVLINK_ANYWHERE_DIR" && sudo ./configure_mavlink_router.sh \
        --headless \
        --uart "$FC_DEVICE" \
        --baud "$BAUD" \
        --skip-serial-check \
        --skip-dashboard \
        --endpoints "127.0.0.1:14540,127.0.0.1:14569"
)
ok "mavlink-router configured and (re)started."

bold ""
bold "=================================================================="
bold " Step 6/6 - Self-test: confirm real MAVLink bytes are flowing"
bold "=================================================================="
info "Listening on local UDP 14540 for 5 seconds..."
python3 - "$GCS_PORT" <<'PYEOF'
import socket, sys

s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
s.bind(("127.0.0.1", 14540))
s.settimeout(5)
try:
    data, _ = s.recvfrom(1024)
    if data[0] in (0xFE, 0xFD):
        print(f"  [OK] Received {len(data)} bytes, starts with MAVLink marker 0x{data[0]:02X}")
        print(f"       First bytes: {data[:16].hex()}")
        sys.exit(0)
    else:
        print(f"  [!!] Received {len(data)} bytes but they do not look like MAVLink: {data[:16].hex()}")
        sys.exit(1)
except socket.timeout:
    print("  [XX] No data received in 5 seconds. Check FC power/wiring and re-run.")
    sys.exit(1)
PYEOF
TEST_RESULT=$?

echo ""
if [[ $TEST_RESULT -eq 0 ]]; then
    bold "=================================================================="
    bold " SUCCESS"
    bold "=================================================================="
    JETSON_IP="$(ip -4 -o addr show | awk '/scope global/{print $4}' | cut -d/ -f1 | grep -v '^172\.' | head -1)"
    echo "  mavlink-router is running and streaming live MAVLink data."
    echo ""
    echo "  On your Ground Control PC, connect via UDP to:"
    echo "      Host: ${JETSON_IP:-<this-jetson-ip>}"
    echo "      Port: ${GCS_PORT}"
    echo ""
    echo "  Check status any time with:  mla status"
    echo "  Watch logs with:             sudo journalctl -u mavlink-router -f"
else
    warn "Setup finished but the live-data self-test failed. Check FC wiring/power and run:"
    warn "  sudo journalctl -u mavlink-router -n 50"
    exit 1
fi

The RF-modem question: does the fixed .11 / .12 address matter?

The MK32 air unit (.11) and ground unit (.12) ship with fixed IPs that can't be changed — meaning every one of the five drones will have identical addresses for these two devices once all five ground units land on one switch. A duplicate IP only matters if something tries to resolve or route to it. To check whether these devices announce themselves at all, we captured 45 seconds of broadcast and multicast traffic — plus anything addressed to .11/.12 directly — on the Jetson's network interface:

$ sudo tcpdump -i enP8p1s0 -n -tttt -e \
    '(broadcast or multicast or host 192.168.144.11 or host 192.168.144.12)'

44 packets captured
49 packets received by filter
0 packets dropped by kernel
Packets captured per source, 45-second window
Filtered for broadcast, multicast, and any traffic to/from the two fixed RF-modem addresses
.11 — air RF modem
0 pkt
.12 — ground RF modem
0 pkt
.10 — other (likely the PC)
44 pkt

Result: zero packets from either fixed RF-modem address. The only traffic seen was a 1 Hz, 72-byte multicast from 192.168.144.10 — most consistent with a ground-station app's own discovery beacon, since mla status already shows an explicit telemetry endpoint pointed at that same address. That source is a single PC, not a per-drone device, so it doesn't multiply when more drones join the switch.

Conclusion: duplicating .11/.12 across all five drones is confirmed safe, not just assumed safe. Nothing in the data path ever needs to resolve those addresses, and the modems themselves stay silent on the wire.

05 Plan: from one drone to five

Same building block, repeated five times, landing on one shared switch with one PC running MAVSDK against all of them at once.

IP allocation scheme

Only the Jetson (and camera / handset, already handled) need a per-drone unique address. The RF-modem IPs are identical everywhere by design and proven harmless.
DeviceDrone 1Drone 2…Drone 5Configurable?
Jetson (mavlink-router).31.32….35Yes — already proven
Camerauniqueunique…uniqueYes — already done
MK32 handset / Android layeruniqueunique…uniqueYes — confirmed
MK32 air unit RF modem.11.11….11No — fixed, proven silent
MK32 ground unit RF modem.12.12….12No — fixed, proven silent

Roadmap

  1. Assign and apply the IP scheme. Set each Jetson's Ethernet interface to a unique static IP (.31–.35), matching the pattern already validated on Drone 1.
  2. Roll the script out. Copy setup_single_drone_telemetry.sh onto each of the other four Jetsons and run it — no changes needed, it self-detects each flight controller.
  3. Wire it all into one switch. Connect all five MK32 ground units and the PC to the shared unmanaged switch.
  4. Verify all five links simultaneously. From the PC, confirm live MAVLink on 192.168.144.3N:14550 for N = 1..5 at the same time — the same self-test the script already runs, pointed at each Jetson.
  5. Build the MAVSDK fleet layer. One Python process on the PC, five System() connections (udp://192.168.144.3N:14550), keyed by drone ID — telemetry subscriptions in, arm/takeoff/land/RTL/mission commands out, dispatched to whichever drone ID is targeted.
  6. End-to-end fleet test. All five telemetry streams live on the PC at once, with an individual command sent to and acknowledged by each drone in turn.
Open item, low priority: the identity of 192.168.144.10 is inferred (most likely the PC's own GCS software), not directly confirmed. It doesn't block anything — it's a single, non-multiplying, negligible-rate source — but worth a quick look in the Siyi/GCS config screens before wiring five drones together, purely for a clean inventory.
